How it works

  1. Baseline. The project is installed in a fresh Docker container with the new library version, and its own test suite runs. Failures are grouped by root cause and handed to the model.
  2. Agent loop. The model can only act through MCP tool servers: read and edit the repo, run the tests in the sandbox (structured summaries, not raw logs), and search the official migration guide with hybrid keyword + embedding retrieval.
  3. Finish is a request, not a declaration. The loop re-runs the full suite itself and only accepts a pass.
  4. Reviewer agent (multi-agent mode). A second agent with a fresh context and read-only tools hunts for old API the tests can't see and sends file:line findings back to the migrator.
  5. Human review. Automatic checks flag weak version pins, compatibility shims and test edits; nothing becomes a branch until a person approves it. The model never gets git access.

Multi-agent: a reviewer that finds what tests miss

Measuring completeness showed one gap: on pydantic-cli, every single-agent run passed all tests but left Pydantic v1 config in the package's examples. The reviewer agent was built to close exactly that gap.
